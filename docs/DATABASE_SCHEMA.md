## Discovery tables (Phase 3, migration `20261123000000_phase3_discovery`)

| Table         | Model        | Purpose                                                  | Key fields                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------- | ------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| discovery_run | DiscoveryRun | One discovery job; also the worker's queue               | area, categories[], provider, status (queued/running/succeeded/failed/cancelled), idempotencyKey (unique), resolved bbox + areaDisplayName, completedCategories[], found/created/updated/duplicate/skipped/request counts, attempts, error, lockedBy/lockedAt, startedById/startedByLabel                                                                                                              |
| business      | Business     | A discovered business with provenance                    | name, normalizedName, category, subcategory, provider + providerId (unique together), osmType/osmId, alternateIds[], address parts, lat/lon, phone, website, hasWebsite, email, openingHours, source, sourceType, sourceUrl, collectedAt, lastSeenAt, confidence, verificationStatus, license, usageRestrictions, rawTags, firstRunId/lastRunId, status (NEW/REVIEWED/QUALIFIED/DISQUALIFIED/ARCHIVED) |
| geocode_cache | GeocodeCache | Nominatim results shared across processes (usage policy) | key (normalised query), query, provider, displayName, south/west/north/east, sourceUrl, fetchedAt                                                                                                                                                                                                                                                                                                      |

- Indexes: `discovery_run(status, createdAt)`, `discovery_run(createdAt)`; `business(category)`, `(hasWebsite)`, `(status)`, `(lat, lon)`, `(createdAt)`.
- The worker claims runs with `FOR UPDATE SKIP LOCKED`; a stale `running` lock is reclaimed. Upserts on `(provider, providerId)` make re-processing idempotent; fuzzy duplicates (same category, < 50 m, name similarity >= 0.85) are merged and recorded in `alternateIds`.
- `confidence` is a completeness heuristic (0..1), not a verification. MOCK rows have `source = "mock"`, provider `mock-discovery` and names starting with `MOCK`.

## Research tables (Phase 4, migration `20261124000000_phase4_research`)

| Table             | Model            | Purpose                                                        | Key fields                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------- | ---------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| research_run      | ResearchRun      | One website-research job; also the worker's queue (job type 2) | provider (`http-extractor` / `mock-research`), status, idempotencyKey (unique), scopeType (businesses / discovery_run / filter), businessIds[], discoveryRunId, filter (JSON), targetIds[] + resolvedAt (scope frozen at start), total/processed/ok/noWebsite/broken/blocked/error/fact/newFact/conflict/request counts, attempts, error, errors (JSON, last 50), lockedBy/lockedAt, startedById/startedByLabel    |
| business_research | BusinessResearch | Outcome of one business in one run (unique runId + businessId) | status (ok / no_website / broken / blocked / error), httpStatus, requestedUrl, finalUrl, signals (JSON `WebsiteSignals`), summary (plain language, no score), factCount, conflictFields[], requestCount, error, researchedAt                                                                                                                                                                                       |
| research_fact     | ResearchFact     | One value about a business with provenance                     | field, value, normalizedValue, sourceUrl, sourceType (jsonld / microdata / meta / html / header / robots / osm / listing / mock), provider, collectedAt, confidence, verificationStatus (unverified / verified / conflicting / invalid), usageRestriction, firstRunId/lastRunId; Phase 5: verifiedAt, verificationMethod, verificationEvidence, verificationOverride, verifiedById/verifiedByLabel, overrideReason |

- `business.lastResearchedAt` is new (set after every research of that business).
- `research_fact` is unique on `(businessId, field, normalizedValue, sourceUrl)`: re-research refreshes `collectedAt`/`lastRunId`, never duplicates. CHECK constraints cap `value` 1000, `normalizedValue` 400 and `sourceUrl` 500 characters (keeps the unique index within B-tree limits), keep `confidence` in 0..1 and `verificationStatus` / `scopeType` to their allowed values.
- **Listing values are facts too.** At research time the discovery record's phone(s), email, website (or social profile), WhatsApp, opening hours, postcode, address, geo and name are written as facts with `sourceType = osm` (OpenStreetMap) or `listing` (other discovery providers), the record's `sourceUrl`, `collectedAt`, `confidence` and licence text. Every value therefore has one provenance shape; the `business` columns stay as discovered and are not overwritten by website data.
- **Conflict rule** (`detectConflicts` in `packages/core/src/research.ts`): for phone, email, whatsapp, postcode and opening_hours, facts are `conflicting` when the listing (osm/listing) and the website (everything else) both have values and share none. One shared value means agreement; several website values never conflict with each other. It is re-evaluated over all stored facts of the business after each research and only moves facts between `unverified` and `conflicting`; `verified`/`invalid` (Phase 5 verification) and manually overridden facts are never touched by research.
- `confidence` on website facts is extraction-method reliability (JSON-LD 0.8, microdata 0.75, tel:/mailto:/social links 0.7, meta 0.6, free text 0.5), not verification.
- Deleting a business cascades its facts and research rows; deleting a run cascades its `business_research` rows (facts keep `firstRunId`/`lastRunId` as plain ids).

## Verification and qualification tables (Phase 5, migration `20261125000000_phase5_qualification`)

| Table                  | Model                 | Purpose                                                         | Key fields                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | --------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| qualification_run      | QualificationRun      | One verification + qualification job; worker queue (job type 3) | status, idempotencyKey (unique), scopeType (businesses / discovery_run / research_run / filter), businessIds[], discoveryRunId, researchRunId, filter, targetIds[] + resolvedAt, aiEnabled + aiProvider (null when rules-only) + promptVersion, rulesVersion, total/processed/hot/warm/cold/disqualified/error counts, facts checked/verified/invalid, dnsLookupCount, aiOk/aiError, aiInputTokens/aiOutputTokens/aiCostMinor, attempts, error, errors, lock + who/when                                                                  |
| business_qualification | BusinessQualification | Result for one business in one run (unique runId + businessId)  | rulesVersion, score 0-100, tier (hot / warm / cold / disqualified), components {website, contact, category}, reasons JSON `[{code, kind, points, text, factIds[], researchId?}]`, disqualifiedReason (closed / no_contact_channel / duplicate / blocked_category), duplicateOfId, operatingStatus, verification summary JSON, researchId, isMock; AI (separate): aiStatus (off / skipped / ok / error), aiSummary, aiPitch, aiRisks, aiError, aiProvider, aiModel, aiPromptVersion, aiInputTokens, aiOutputTokens, aiCostMinor, aiIsMock |

- `business.latestScore`, `latestTier`, `qualifiedAt` hold the latest rules result for listing (index `(latestTier, latestScore)`); history stays in `business_qualification`.
- **Verification** (`packages/core/src/verification.ts`, deterministic, no AI; rules version `verify-v1`). Phone/WhatsApp: E.164, Indian numbers +91 + 10 digits (11 for 1800/1860), not starting 0, no placeholders, else `invalid`; `verified` when >= 2 independent sources list the number (phone and WhatsApp facts both count; independent = different listing provider or different website host, so pages of one site are one source). Email: syntax, reserved/test and disposable domains `invalid`; MX lookup with timeout and cache: NXDOMAIN / null MX `invalid`, MX ok plus (2 independent sources or domain = business website host) `verified`, timeouts stay `unverified`. Website: latest research reachable `verified`; DNS failure, invalid URL, 404/410, redirect to a private address `invalid`; timeouts, 5xx, TLS and robots-blocked stay `unverified`. Postcode: PIN `^[1-9][0-9]{5}$` else `invalid`; outside the listed state's postal prefixes `conflicting`; 2 independent sources (incl. a PIN inside an address fact) `verified`; city is not checked (no offline PIN directory). Other conflict fields keep the Phase 4 rule, ignoring `invalid` values. Each checked fact gets `verifiedAt`, `verificationMethod` and `verificationEvidence` (reason, sources, MX hosts, research id; `mock: true` when based on MOCK research).
- **Manual override** (`apps/worker/src/verification-store.ts`, backend only, caller enforces RBAC): sets status with `verificationOverride = true`, who (`verifiedById`/`verifiedByLabel`), when and why (`overrideReason`, required; CHECK constraint), keeps the previous automatic result in the evidence and writes `audit_log` `verification.override` / `verification.override_clear`. The automatic pass and research conflict refresh never change an overridden fact; a manually invalidated value does not count as a corroborating source.
- **Still operating:** OSM lifecycle/closed tags (`disused:*`, `was:*`, `abandoned:*`, `shop=vacant`, `opening_hours=closed`, past `end_date`, ...) mean `closed` (disqualified); a website whose domain no longer resolves or returns 404/410 is only `possibly_closed` (a note, no disqualification).
- **Score** (`packages/core/src/qualification.ts`, `rules-v1`): website opportunity max 50 (no website 50, social profile only 45, broken 45; else no https 12, no viewport 12, copyright >= 2 years old 8, dated builder 8, missing title/description 5, slow > 4 s 5), contactability max 35 (verified phone 20 / unverified 10, WhatsApp 10 / 5, email 10 / 4; `invalid` values ignored), category fit max 15. Tiers: hot >= 70, warm >= 45, else cold; disqualified when closed, owner-blocklisted category, duplicate of an older record (fuzzy name < 50 m, or same number + similar name < 2 km) or no usable contact channel. Weights, thresholds, category fit and blocklist are overridable in `system_setting` key `qualification` (zod-validated). The AI step never writes score or tier.
- CHECK constraints: fact status in the four values; override needs label, reason and time; scopeType values; aiEnabled iff aiProvider; score 0..100; tier values; tier = disqualified iff disqualifiedReason; aiStatus values; business latest score/tier ranges.
- Deleting a business cascades its qualifications; deleting a run cascades its `business_qualification` rows.

## Database-level guarantees

- `audit_log` rejects UPDATE and DELETE via triggers (migration `audit_append_only`). Users are therefore suspended, never hard-deleted.
- Money is stored as integer minor units plus ISO currency.
- Secrets are never stored: only environment variable names.
